## 3. 逐项说明

### 3.1 #2558 ext4 符号链接 xattr

`ext4::getxattr` 对 `FileType::SymLink` 返回 `EPERM`，导致 containerd `CreateDiff`
读取 `security.capability` 时整层导出失败（`docker commit` 报
`failed to get xattr ... operation not permitted`）。Linux 6.6 实测（ext4）对符号链接读取
`security.capability`/`user.foo`/`trusted.foo` 均返回 `ENODATA`（VFS 把 `-EOPNOTSUPP`
归一为 `-ENODATA`），写入仍由 `xattr_permission` 拒绝为 `EPERM`。改动只影响读取路径。

验证：净盘上 `docker create` + `docker commit` 成功（`sha256:c33b74e8...`），新镜像可运行并
正确列出 `/bin/arch -> /bin/busybox`。

### 3.2 #2559 #DF IST

任务栈不可用时，原处理器会在坏栈上打印并 panic，最终三重错误复位。改动：
每 CPU 16 KiB 双错栈（`.bss`）、BSP/AP 写入 TSS `IST[0]`、IDT 向量 8 改用 `ist=1`、
处理器只用零分配 COM1 通道输出 `err/cr2/rsp/rip` 后 `cli; hlt`；`printk` 增加
`emergency_print_hex_noalloc`。

拆分时处理了两处与上游的差异：

- `printk.rs` 冲突：上游没有分支上的 `CriticalPrintkWriter`，只手写保留零分配紧急输出块，
  并把注释里对该类型的引用改为“常规 printk 路径”；
- rustfmt 对 `init/mod.rs`、`smp/mod.rs` 的两处改写通过 `--fixup` + `--autosquash`
  合入首个提交，保证两个提交都干净。

验证：gdb 确认 `TSS.ist[0]` 与门 8 的 IST 字段；清零双 CPU `TSS.RSP0` 后 ring3 忙循环，
下一次定时中断得到 `[#DF] double fault (IST): ... -- halted`，未三重错误复位。

### 3.3 #2560 TLB shootdown 入站服务

死锁链：CPU0 持 `FLUSH_TLB_GLOBAL_LOCK` 等 IPI ack；CPU1 在关中断里自旋争用同一把锁，
无法进入 IPI handler → 双方互等。开启 guard page 后每次栈分配/释放都会 flush guard 映射，
容器启动负载下必现。

修复分两部分（两个提交）：

1. `acquire_flush_tlb_lock()`：等锁期间调用 `service_pending_inbound_flush()`，按 IPI handler
   同一流程就地执行 `local_flush_tlb_func` 并置 `done`；ack 轮询每 1024 次也服务一次；
2. **IRQ-safe 就地服务**（CI 阶段发现的新缺陷）：就地服务可能在开中断上下文运行。
   - 若取走 CSD 指针后、flush 前被本 CPU 的 IPI 打断，handler 看到 `None` 提前置 `done`，
     发起者会在 flush 完成前返回（违反 INV-4）；
   - 更严重：若持锁用不关中断的 `lock()`，IPI handler 会在**同一 CPU** 上自旋等待
     “被它打断、正在挂起”的持锁者 → 自死锁。
   用 `lock_irqsave()` 全程持锁并取指针，IPI 被推迟到 flush 完成、放锁之后。

自死锁的复现与验证：`KERNEL_FEATURES=mm_selftest` 内核启动即挂（gdb：CPU1 在
`flush_tlb_multi` 等 ack，CPU0 在 `remote_flush_tlb_on_ipi` 抢自己的 CSD 锁）；
改用 `lock_irqsave` 后同一内核正常启动到 console。CI 上该 PR 的 Dunitest/Integration 从
稳定失败变为全部通过。

### 3.4 #2561 默认启用 kstack_protect

内核栈溢出目前会静默写穿栈底 PCB 槽及下方内存，之后表现为 `current_pcb` 失败或伪随机
内存破坏。开启 guard 后溢出变为可定位缺页，栈底损坏类故障变为 #DF（配合 #2559 输出现场）。
代价是每任务多一份栈大小的**虚拟**地址窗口。

前置条件：TLB 互等已修（#2560）、journal 提交路径的 4 KiB 栈临时上游已消除
（`try_filled_bytes`/`try_copy_bytes`）。因依赖 #2560 先合入，PR 以 **Draft** 提交。

验证：12G/4G 下 OCManager 七容器 + 三服务全流程 RC=0、健康 200；脏 journal 重启无 panic/#DF；
CI 全部通过。

### 3.5 #2562 stub 架构堆布局判定（CI 解阻，新增）

`origin/master` 的 `Build loongarch64` 在 #2554 之后必然失败：

```
error[E0080]: evaluation panicked: assertion failed: !HeapPlan::prefers_virtual_layout(source)
  --> src/filesystem/epoll/epitem.rs:52:5
```

LoongArch64 仍是 stub：`MemoryManagementArch::PAGE_SHIFT = 0` ⇒ `PAGE_SIZE = 1`，于是
`prefers_virtual_layout()` 对任何真实分配都返回 true，触发 `epitem.rs` 的编译期布局断言。
stub 架构没有页粒度、其堆本来也只走 physical/direct 路径，因此在
`prefers_virtual_layout()` 里对 `PAGE_SHIFT == 0` 直接返回 `false`。

验证：`make kernel ARCH=loongarch64` 修复前 E0080、修复后 `Kernel Build Done`；
`make kernel`（x86_64）与 `make -C kernel fmt` 通过。
